# Fix for "POST /api/auth/register → 404" on Vercel

## Why the 404 happened

The project has two parts:

- `frontend/` — a TanStack Start (Vite + Nitro) React app. In local development,
  the Vite dev server proxies every `/api/*` request to the Express backend
  running on `localhost:3000` (`frontend/vite.config.ts`).
- `backend/` — an Express + Mongoose REST API.

Your Vercel deployment (`food-nest-source-code.vercel.app`, branch `main`) only
shipped the built **frontend**. The Nitro server (`/__server`) renders the React
pages, but nothing in the deployment owns the `/api/*` routes — the Express
backend was local Node code that never got deployed. So `POST /api/auth/register`
correctly returned 404: the route simply does not exist in production.

## What this fix does

Instead of hosting the backend separately (which would require two domains and
CORS), the API is now bundled into the **same Vercel deployment**:

1. **`frontend/vite.config.ts`** — the Nitro build preset was changed from
   `cloudflare-module` to `vercel`, so `npm run build` now emits a proper Vercel
   output (`frontend/.vercel/output/`) including the `__server` function that
   matches the route in your deployment log.

2. **`scripts/build.js`** — a new build script that (a) builds the frontend, then
   (b) patches the generated `__server.func/index.mjs` so that requests to
   `/api/*` and `/uploads/*` are dispatched to the shared Express app
   (`backend/server.js`), while everything else falls through to the existing
   SSR renderer. The Express app is imported lazily, so cold starts stay fast.

3. **`backend/server.js`** — the `app.listen()` call is now guarded so the
   Express server only starts when run directly (`node server.js`). When imported
   as a module inside the Vercel function, the host runtime owns HTTP and only
   the routes are used.

4. **`package.json`** (project root) — declares the backend dependencies and sets
   `"build": "node scripts/build.js"` so Vercel runs the unified build.

## How to redeploy

1. Push this updated code to your GitHub `main` branch (or upload to Vercel).
2. In the Vercel project settings, set:
   - **Root Directory**: (leave at the repository root — this project deploys
     from the root, not the `frontend/` folder)
   - **Build Command**: `node scripts/build.js`
   - **Output Directory**: leave blank (Vercel auto-detects
     `frontend/.vercel/output`)
3. Add these **Environment Variables** (Vercel → Settings → Environment
   Variables), which the backend needs at runtime:
   - `MONGODB_URI` — your MongoDB connection string
   - `JWT_SECRET` — a long random secret
   - `GOOGLE_CLIENT_ID` (optional) — if you use Google sign-in
4. Deploy. `POST /api/auth/register` and all other `/api/*` routes will now work
   on the same domain.

## Verification

The full flow was tested end-to-end against the **patched built output** (same
code that Vercel will run), with the database mocked:

| Check | Expected | Result |
|---|---|---|
| `POST /api/auth/register` | 201 + 2FA code | Pass |
| `POST /api/auth/register/verify-2fa` | 200 + token | Pass |
| `POST /api/auth/login` | 200 + token | Pass |
| `POST /api/auth/register` (duplicate) | 400 | Pass |
| `GET /api/health` | 200 | Pass |
| `GET /api/nonexistent` | 404 (Express) | Pass |
| `GET /` (frontend page) | 200 (SSR fallback) | Pass |

The frontend pages continue to be server-rendered exactly as before; only
`/api/*` and `/uploads/*` requests are now handled by the Express backend.
